# 番外. サブエージェントとスキルの分け方: 23 パターンの地図

> **この章が答える問い**: サブエージェント開発で、エージェントやスキルを何の単位で分けるか(機能グループ別か、職能別か、工程別か…)。粒度をどう決めるか

> **位置づけ**: Spartacus の調査そのものではない番外編。25 章で「フロントとバックの責務」を分けたのと同じ考え方を、エージェントとスキルの分け方に当てはめる

> **根拠の取り方**: 点数(1〜5)は筆者がパターンの性質から付けた目安で、測定値ではない。散布図で軸を切り替えて見られる対話版は [extras/agent-split-map.html](extras/agent-split-map.html)(ダウンロードしてブラウザで開く)

### 先に話し言葉で: エージェントを分ける理由は 3 つだけ

エージェントを分ける理由は、大量の読み込みで親の文脈を汚したくないとき、並列で速くしたいとき、権限や視点を分けたいときの 3 つです。どれにも当たらないなら、エージェントは 1 つのままにして、スキルで専門性を足します。分けるなら、境界は「引き継ぎが少ない線」に引きます。エージェント同士は要約でしか話せないからです。スキルの粒度は「一緒に読まれるもの」で決めます。

### 軸

| 軸 | 1 | 5 |
|---|---|---|
| 粒度 | 粗い | 細かい |
| 切り口 | 何を作るか(業務・機能) | どう作るか(技術・工程) |
| 文脈の軽さ | 重い | 軽い |
| 引き継ぎの少なさ | 多い | 少ない |
| 並べやすさ | 低い | 高い |
| 再利用しやすさ | 低い | 高い |
| 責務の明確さ | 曖昧 | 明確 |
| 保守の軽さ | 重い | 軽い |

文脈の軽さ・引き継ぎの少なさ・並べやすさは、スキルでは「必要なときだけ小さく読まれるか」「他のスキルを参照せずに済むか」「他のスキルと組み合わせやすいか」と読む。

**A1 機能グループ別**
- 向いている場面: 機能ごとに技術も担当者も分かれていて、機能同士の結合が弱いとき。1 つの依頼が 1 つの機能で閉じることが多いとき。
- 避けたい場面: 機能をまたぐ変更(共通部品や認証)が多いとき。各エージェントが同じ規約を別々に持ってしまい、ずれやすい。
- コツ: 共通の規約は「規約スキル」に出して、全エージェントに同じものを読ませる。

**A2 職能・レイヤ別**
- 向いている場面: 人のチーム編成に合わせたいとき。レイヤごとに道具と規約がはっきり違うとき(Angular と Java など)。
- 避けたい場面: 1 つの機能を作るのに API の形を何度も往復するとき。要約での引き継ぎが増え、境界で食い違う。
- コツ: 境界の契約(OCC の項目名、fields、エラーの形)を成果物として固定し、それを両方に渡す。

**A3 業務ドメイン別**
- 向いている場面: 業務の境界(境界づけられたコンテキスト)がはっきりしていて、用語や規則がドメインごとに違うとき。
- 避けたい場面: ドメインの境界がまだ決まっていない初期。境界の引き直しのたびにエージェントを作り直すことになる。
- コツ: ドメイン知識はスキル(業務知識スキル)にし、エージェントは薄く保つ。

**A4 工程別**
- 向いている場面: どの機能でも同じ流れで進めたいとき。工程ごとに必要な道具と権限が違うとき。
- 避けたい場面: 工程の前後で同じ情報を何度も読み直すとき。直列なので並列化しにくく、遅い。
- コツ: 工程の間は、計画書や差分のようなファイルで渡す。要約だけで渡すと、細部が落ちる。

**A5 視点・役割別**
- 向いている場面: 自分の仮説に引きずられない見方がほしいとき(レビュー、反証、セキュリティ確認)。
- 避けたい場面: 批評役に結論を渡してしまうとき。仮説を渡すと「確認しました」が返ってきやすい。
- コツ: 批評役には結論ではなくコードと要件だけを渡す。

**A6 権限・ツール境界別**
- 向いている場面: 事故の範囲を限りたいとき。本番やデータ削除に触れるエージェントを 1 つに閉じたいとき。
- 避けたい場面: 権限だけで分けて仕事の中身を決めないとき。結局どれに頼むか迷う。
- コツ: 他の分け方と重ねて使う(例: 工程別 × 権限別)。

**A7 データ分割(fan-out)**
- 向いている場面: 同じ作業を大量の対象に当てるとき(全ファイルの棚卸し、100 シナリオの検証)。
- 避けたい場面: 対象同士に依存があるとき。結果をまとめる側の負担が大きくなる。
- コツ: 出力の形(表の列やスキーマ)を先に決めて全員に渡すと、まとめるのが楽になる。

**A8 モデル・コスト別**
- 向いている場面: 量が多い単純作業と、少数の難しい判断が混ざっているとき。
- 避けたい場面: 軽いモデルの判断ミスがそのまま後ろに流れるとき。
- コツ: 軽いモデルの出力は、重いモデルか機械的な検査で確かめる。

**A9 ジェネラリスト 1 つ + スキル**
- 向いている場面: 小さなチームや小さなリポジトリ。引き継ぎによる品質低下を避けたいとき。
- 避けたい場面: 大量の読み込みで文脈があふれるとき。並列で速くしたいとき。
- コツ: まずこれで始め、文脈があふれた作業だけをエージェントに切り出す。

**A10 オーケストレーター + 専門ワーカー**
- 向いている場面: 大きな作業を分解して並列に進め、最後に統合したいとき。
- 避けたい場面: まとめ役の計画が粗いとき。ワーカーが同じ範囲を重複して触る。
- コツ: ワーカーの範囲を明示し、触ってよいファイルを分ける(worktree を分けるのも手)。

**A11 モジュール・リポジトリ別**
- 向いている場面: コードの所有範囲がパッケージで決まっていて、パッケージごとに規約やビルドが違うとき。
- 避けたい場面: 変更の多くがパッケージをまたぐとき。
- コツ: パッケージの公開 API(Facade など)を境界の契約として扱う。

**A12 イベント・タイミング別**
- 向いている場面: 起動のきっかけごとに、やることと読む情報がはっきり違うとき。
- 避けたい場面: 同じ処理を複数のきっかけで重複して持つとき。
- コツ: 処理そのものはスキルにまとめ、イベント別のエージェントはそれを呼ぶだけにする。

**A13 利用者・ペルソナ別**
- 向いている場面: 相手によって口調、公開してよい情報、権限が違うとき。
- 避けたい場面: 裏でやる処理がほぼ同じとき。同じ知識が重複する。
- コツ: 共通の知識はスキル、相手ごとの違いはエージェント側の指示に置く。

**A14 成果物別**
- 向いている場面: 成果物ごとに書き方の型と検証方法が違うとき(図は生成スクリプト、ドキュメントは引用の検証)。
- 避けたい場面: 成果物同士の整合(コードと説明の一致)が重要なとき。
- コツ: 整合は最後に 1 つのエージェントで照合する。

### スキルの分け方(9)

|---|---|---|---|---|---|---|---|---|---|---|

| S9 | 領域まるごとスキル(段階的に読み込む) | 「フロント開発」1 つ。本文は目次、詳細は references/ | 1 | 4 | 3 | 4 | 3 | 4 | 3 | 3 |

**S1 手順スキル(1 手順 = 1 スキル)**
- 向いている場面: 毎回同じ順番でやる作業。抜けると事故になる作業。
- 避けたい場面: 手順が案件ごとに大きく変わるとき。分岐だらけになる。
- コツ: 確認コマンドと失敗時の戻し方まで書く。

**S2 規約・スタイルスキル**
- 向いている場面: どのエージェントにも同じ書き方を守らせたいとき。
- 避けたい場面: 規約を全部詰め込んで毎回大量に読ませるとき。
- コツ: よく破られる規則だけを短く。残りはリンターに任せる。

**S3 ドメイン知識スキル**
- 向いている場面: コードからは読み取れない業務の前提が多いとき。
- 避けたい場面: 知識が古くなっても誰も更新しないとき。
- コツ: 出典と更新日を書き、コードで確かめられることは書かない。

**S4 ライブラリ・フレームワークスキル**
- 向いている場面: フレームワーク固有の「どこに何を書くか」の規則が多いとき。
- 避けたい場面: 公式ドキュメントの丸写し。古くなりやすく、長い。
- コツ: Spartacus 2612 の spartacus-developer のように、本文は目次にして references/*.md に分ける。

**S5 チェックリスト・レビュー観点スキル**
- 向いている場面: レビュー役のエージェントに観点を持たせたいとき。
- 避けたい場面: 観点が多すぎて全部が浅くなるとき。
- コツ: 観点ごとに 1 スキル。重大度の基準も書く。

**S6 テンプレート・生成スキル**
- 向いている場面: 同じ形の成果物を何度も作るとき。
- 避けたい場面: 型が合わない成果物にまで当てはめるとき。
- コツ: 完成例を 1 つ添える。型だけより再現性が上がる。

**S7 参照・カタログスキル**
- 向いている場面: 引くための表が要るとき。
- 避けたい場面: 表が大きく、毎回全部読ませるとき。生成元から自動で作らないと古くなる。
- コツ: 表は別ファイルにして、必要な行だけ grep させる。

**S8 ワークフロースキル(手順を束ねる)**
- 向いている場面: 複数の手順を決まった順に呼び、途中で人の確認を挟みたいとき。
- 避けたい場面: 中身を全部 1 つに書くとき。長く、部分的な再利用ができない。
- コツ: 中身は手順スキルに分け、ワークフローは呼び出し順だけを書く。

**S9 領域まるごとスキル(段階的に読み込む)**
- 向いている場面: 1 つの領域の知識が多いが、毎回使うのはその一部というとき。
- 避けたい場面: 目次が曖昧で、どの詳細ファイルを読むべきかエージェントが判断できないとき。
- コツ: 目次の各行に「いつ読むか」を書く。

### 規模別の組み合わせ例

| 規模・状況 | エージェント | スキル | 説明 |
|---|---|---|---|
| 1〜3 人、1 リポジトリ | 単一+スキル・視点別 | ライブラリ・手順・チェック | エージェントは基本 1 つ。レビューのときだけ批評役を分ける。専門性はライブラリスキルと手順スキルで足す。 |
| 5〜15 人、フロントとバックが別チーム | 職能別・視点別・権限別 | ライブラリ・領域まるごと・規約・チェック | 職能別にエージェントを分け、API の契約(OCC の項目、fields、エラー)は成果物として固定して渡す。探索は読み取り専用エージェントに任せる。 |
| 大規模 monorepo、並列で進めたい | 階層型・モジュール別・データ分割 | ワークフロー・規約・手順 | まとめ役がパッケージ単位で配り、棚卸しのような量の多い作業は fan-out する。ワークフロースキルで呼び出し順を固定する。 |
| 運用・定型作業が中心 | イベント別・権限別 | 手順・ワークフロー | PR 時、障害時、定期実行で起動を分け、中身は手順スキルに置く。本番操作は権限を分けたエージェントに閉じる。 |
| 業務ルールが複雑(EC の価格・在庫など) | ドメイン別・視点別 | 業務知識・カタログ・チェック | ドメインごとに分け、業務知識スキルに規則と出典を書く。改ざんや計算の誤りは検証役で確かめる。 |
| この調査ノートのようなドキュメント作り | データ分割・視点別・成果物別 | テンプレ・チェック・手順 | 引用の確認は fan-out、主張の反証は批評役が担う。章の型はテンプレートスキル、同期と push は手順スキルに置く。 |
